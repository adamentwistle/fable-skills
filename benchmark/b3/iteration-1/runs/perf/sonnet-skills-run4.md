1. On-call proposal: don't ship it as-is — more workers/pool connections just let more of the same slow, memory-leaking requests run concurrently, and it hits the same DB bottleneck faster; the Redis cache masks it for 60 s but the leak and the p95 spike on cache miss remain.
2. Root fix, query: no index on `(org_id, created_at)` — the SELECT does a full scan of 4.2M rows filtered/sorted in memory; add `CREATE INDEX events_org_created_idx ON events (org_id, created_at DESC)`.
3. Root fix, query: `since` is unbounded on the high end and dedup/limit happen in Python after fetching the whole 30-day window — push `ORDER BY created_at DESC LIMIT $3` into SQL (using dedupe at insert/write time, or a `DISTINCT ON (dedupe_key)` query) instead of loading up to thousands of rows to keep 200.
4. Root cause, memory leak: `_geo_cache` is an unbounded module-level dict keyed by every client IP ever seen, never evicted — this is the RSS growth from 310MB to 2.1GB; bound it (LRU with a cap/TTL) or move geo lookups to a real cache (Redis) with expiry.
5. Root cause, blocking healthz: `lookup_geo` uses synchronous `requests.get` inside an async endpoint, blocking the event loop for up to 2 s per uncached IP on every request — this is why `/healthz` stops responding; switch to an async HTTP client (httpx.AsyncClient) or batch/cache geo lookups so they're rare.
6. N+1 query: `serialize_event` does one `SELECT ... FROM users` per event — for 1000 events that's 1000 round trips; batch-fetch actors with a single `WHERE id = ANY($1)` keyed on distinct actor_ids.
7. `_request_timings` is also an unbounded list appended on every request forever — bound or roll it into a proper metrics counter (adds to the same leak pattern, lower priority than `_geo_cache`).
8. After 2–6 are done, re-measure p95 for acme/northwind; only then consider a short-TTL response cache (30–60 s) as a smoothing layer, not a substitute — and definitely don't raise worker/pool counts until the per-request work is fixed, or you'll just OOM faster.
