1. Backfill's OFFSET pagination skips every other batch: each UPDATE removes rows from the `state IS NULL` set, so the next OFFSET jumps past unprocessed rows (staging's "1055000 of 2104377" is this bug, not a stat); paginate by `id > last_id` with no OFFSET and loop until the SELECT returns nothing.
2. The CASE has no ELSE, so `PAID`, `canceled`, `complete` and the 149 NULLs (7,764 rows) map to NULL and stay NULL forever, which makes 0143's SET NOT NULL fail; normalise with `lower(trim(status))`, map `canceled`→3, decide `complete` and the NULLs with product, and make the script abort if any distinct status is unmapped before it starts.
3. The whole backfill runs in one transaction, holding row locks on every updated order for hours, so `mark_paid` webhooks block, retry and pile up, WAL and bloat balloon, and any crash rolls back everything (so "safe to re-run" means "start over"); commit per batch and sleep briefly between batches.
4. Prod runtime is at least 61M/2.1M × 11 min ≈ 5.5 h even before the quadratic OFFSET cost, so the backfill cannot fit "all in the Thursday window"; run it over days ahead of the cutover, not as a deploy step.
5. Step 2 deploys code that does `OrderState(row["state"])` before step 3 has backfilled, so every `get_order` on an unbackfilled row raises ValueError (500s) for the entire backfill duration; add a dual-write/dual-read release first (write both columns, read `state` with fallback to `status`), and only switch to state-only after backfill is verified complete.
6. During the 6-minute rolling deploy, old pods create orders with `status='pending'` and state NULL while new pods create orders with state only, so `mark_paid` on either side silently misses orders created by the other (the webhook still gets a 2xx, so the provider will not retry); dual-write fixes this too.
7. `jobs/nightly_finance_export.py` reads `o.status` and filters `IN ('paid','shipped')`; the grep was limited to `app/`, so 0143 breaks Friday's 02:00 UTC Finance export; port it to `state IN (1, 2)` in this PR and grep the whole repo, not `app/`.
8. Two read replicas serve external consumers (Looker, ETL, ad-hoc) whose SQL is not in this repo; check `pg_stat_statements` on both replicas for queries touching `orders.status` before dropping the column.
9. `ALTER COLUMN state SET NOT NULL` in 0143 scans all 61M rows under ACCESS EXCLUSIVE, blocking every read and write for minutes and queueing behind any long query; add `CHECK (state IS NOT NULL) NOT VALID`, `VALIDATE CONSTRAINT`, then SET NOT NULL (PG15 skips the scan), then drop the check, all with `lock_timeout` set.
10. 0143's downgrade re-adds `status` as an empty column, so a rollback after step 4 leaves the old app reading NULL statuses; keep `status` for at least one release and drop it in a separate PR after a soak.
11. `kubectl run` defaults to `--restart=Always`, so the pod re-runs the script on exit and on every crash; use a Job with `--restart=Never`, and make the script resumable (per-batch commits from item 3 give you that).
12. `done` counts rows selected, not rows changed, so the final "rows updated" line is wrong; use `cur.rowcount` and print the count of rows still NULL at the end.
13. Nothing tests the migration path: the suite runs on a fresh schema, so neither the backfill nor the odd status values are exercised; run the backfill against a prod snapshot and add a preflight in 0143 that asserts `count(*) WHERE state IS NULL = 0`.
14. Before 0142: verify `CREATE INDEX CONCURRENTLY` succeeded (`indisvalid`) after it runs, since a failed concurrent build leaves an invalid index the migration will not notice.
15. Before the backfill: run `SELECT DISTINCT lower(trim(status))` on prod and confirm every value has a mapping (item 2), and watch replica lag while batches run.
16. Between backfill and 0143: confirm zero NULL `state` rows and that the export in item 7 and every replica consumer in item 8 have been ported and run green at least once.

This cannot ship Thursday as planned. What can ship Thursday is 0142 plus a dual-write app release; the fixed backfill then runs over the following days, and 0143 goes out in a later release once items 2, 7, 8 and 16 are verified.
