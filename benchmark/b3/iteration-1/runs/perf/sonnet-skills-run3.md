1. No — don't ship the proposal as-is; it masks four real bugs and the pool bump risks exhausting Postgres connections (16 workers × 50 × 6 pods = 4800).
2. Root cause of the 1.2-1.6s query: no index covers `(org_id, created_at)` — only `actor_id` and `kind` are indexed, so every call is a sequential-ish scan filtering 4.2M rows down to ~1.9k for acme. Fix: add `CREATE INDEX events_org_created_idx ON events (org_id, created_at DESC)`.
3. The query has no `LIMIT` — it fetches every event in the 30-day window (all ~1.9k rows for acme) and only slices to `limit` in Python after full fetch+serialize. Fix: push `ORDER BY ... LIMIT` into SQL (dedupe first, or fetch a bit over `limit` to allow for dedupe collapse).
4. `serialize_event` does one `SELECT` per event for the actor — an N+1 that's up to 1000 round-trips per request, the actual multiplier behind the pg log volume. Fix: batch-fetch all actors once with `WHERE id = ANY($1::bigint[])` and join in memory.
5. `lookup_geo` calls `requests.get` synchronously inside an `async def` request path — this blocks the whole event-loop thread for up to 2s per uncached IP, which is exactly why `/healthz` stops answering mid-request and the liveness probe kills pods. Fix: use an async HTTP client (`httpx.AsyncClient`) or push the sync call to a thread pool via `run_in_executor`.
6. `_geo_cache` and `_request_timings` are unbounded module-level containers that only grow — that's the RSS climb to 2.1 GB, not a normal working-set increase. Fix: bound `_geo_cache` (TTL/LRU cache) and cap `_request_timings` (e.g. `collections.deque(maxlen=N)`).
7. Dedupe uses `if key in seen` against a growing Python list — O(n²) over up to thousands of rows per request. Fix: use a `set` for `seen`.
8. Do 2–7, then re-measure acme's p95 and pod RSS growth before touching anything else.
9. Only after that: Redis response cache at 60s is reasonable for this read-heavy endpoint and fine to add — but it's a latency band-aid for repeat requests, not a fix for the DB/event-loop/leak issues above, so land it last, not first.
10. Leave workers/pool as-is until 2–7 land and you re-measure; if p95 is still high only then raise them, and size the pool bump against Postgres `max_connections`, not just per-worker throughput.
