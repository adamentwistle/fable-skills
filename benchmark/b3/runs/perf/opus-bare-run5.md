1. Do not ship the on-call proposal — 16 workers × pool max 50 × 6 pods = up to 4,800 Postgres connections (will exhaust `max_connections`), and neither change touches the two actual causes; a 60 s cache still leaves every miss blocking the event loop, and more workers multiply the leak per pod.
2. `CREATE INDEX CONCURRENTLY events_org_created_idx ON events (org_id, created_at DESC)` — no index starts with `org_id`, so every call scans 4.2M rows to return 1,912; this is the 1.2–1.6 s slow query.
3. Push the dedupe and the limit into SQL (`DISTINCT ON (dedupe_key)` in a subquery, then `ORDER BY created_at DESC LIMIT $3`) — the handler fetches every row in the 30 d window and only slices to `limit` after materializing and deduping all of them in Python.
4. Replace the per-event actor `fetchrow` with one `WHERE id = ANY($1)` batch fetch (or a join) — 1,912 events currently mean 1,913 round trips on a pool of 10, and it is sequential `await` per event.
5. Make `lookup_geo` non-blocking — it uses `requests` inside an async handler, so each uncached IP freezes the whole worker's event loop for up to 2 s; use an async client, and cap concurrency. This is why `/healthz` stops answering and the 3 s liveness probe restarts pods.
6. Bound `_request_timings` — it grows one float per request forever at ~120 req/s, which is the RSS climb from 310 MB to 2.1 GB over 20 h; swap it for a fixed-size deque or a counter/bucket histogram, and note `/internal/metrics` currently sorts the entire list on every scrape.
7. Bound `_geo_cache` too — it is keyed on client IP and never evicted, so it leaks alongside the timings; use an LRU with a max size and a TTL.
8. Run `EXPLAIN (ANALYZE, BUFFERS)` for org 4127 before and after steps 2–4 to confirm the plan flips to an index scan and rows-read drops to roughly `limit`.
9. Re-check the pod after deploy: RSS should be flat over several hours at steady traffic, and `/healthz` should answer under 3 s while an acme request is in flight.
10. Only then revisit sizing, and if so raise workers modestly (4 → 6-8) with pool max *lowered*, budgeting total connections as workers × pods × pool_max against `max_connections`; a Redis cache is optional after this and would want a shorter key set than `(org_id, since, limit)`, since `since` defaults to a per-request timestamp and never repeats.
11. Separately, tell the mobile team `limit=1000` is far past what the Activity tab renders — dropping it to ~50 with a cursor cuts the remaining work by 20×.
