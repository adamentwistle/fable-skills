1. Do not ship the on-call proposal. Neither half works, and both make the paging worse.
2. The Redis cache would have a ~0% hit rate: `since` defaults to `datetime.now(timezone.utc) - 30d`, so the cache key is unique per request down to the microsecond.
3. 16 workers × pool max 50 × 6 pods = up to 4,800 Postgres connections, far past a default `max_connections`; and 16 workers each leaking to 2 GB makes the OOM-kill arrive sooner, not later.
4. Root cause of the pages (not the latency): `lookup_geo` is a synchronous `requests.get` inside an async handler, so up to 1,000 sequential 2 s-timeout HTTP calls block the event loop — that is why `/healthz` stops answering and the 3 s liveness probe restarts pods. Fix: async client, concurrent with a bounded semaphore, or move geo enrichment off the request path entirely.
5. Root cause of the RSS climb: `_request_timings` grows one float per request forever at ~30 req/s per worker, and `_geo_cache` grows one entry per distinct client IP forever. Fix: bounded ring buffer (or a real histogram) and an LRU with a size cap.
6. `/internal/metrics` calls `sorted()` on that multi-million-element list — a large synchronous allocation that also stalls the loop; the ring buffer fixes this too.
7. Run `EXPLAIN (ANALYZE, BUFFERS)` on the logged query with `$1=4127`, and again for a <50-event org, before changing the schema — the 0.18 s small-org p50 is inconsistent with a full seq scan on every request, and the plan tells you whether the 1.2–1.6 s is the scan or is proportional to rows returned.
8. Finding regardless of what EXPLAIN says: there is no index usable by this query. `WHERE org_id = $1 AND created_at >= $2 ORDER BY created_at DESC` has only `actor_id` and `kind` indexes to choose from, against 4,213,660 rows. Fix: `CREATE INDEX CONCURRENTLY ON events (org_id, created_at DESC)`.
9. The query has no `LIMIT`, so it returns every row in the 30 d window (1,912 for acme) and Python throws most away. Fix: push dedupe and `LIMIT` into SQL — `DISTINCT ON (dedupe_key)` ordered so the newest wins, then order by `created_at DESC LIMIT $3` — which preserves the current dedupe-then-truncate semantics; a bare `LIMIT` before dedupe would not.
10. `seen` is a list, so `ev["dedupe_key"] in seen` is O(n²) — ~1.8 M comparisons for acme. Fix: a set. Cheap, and irrelevant once step 9 lands.
11. `serialize_event` does one `fetchrow` per event, so 1,000 events is 1,000 sequential round trips on a single pooled connection. Fix: one `WHERE id = ANY($1)` for the distinct actor IDs, then look up from a dict.
12. Re-measure after each change with the same Datadog p95 for org 4127 and org 88, and separately poll `/healthz` while an acme request is in flight — the probe restarts are the P1, and only step 4 fixes them.
13. Keep `limit=1000` for now; once 9 and 11 land, ask the mobile team whether the Activity tab actually renders 1,000 items or should page at 50.
14. If you must ship something in the next hour, ship steps 4, 5 and 8 — the index, the async geo call, and the two bounds. They stop the pages and the OOM kills without touching worker or pool counts.
