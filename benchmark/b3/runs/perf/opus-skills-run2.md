1. Do not ship the on-call proposal — 16 workers × pool max 50 × 6 pods is up to 4,800 Postgres connections (server almost certainly has ~100-500), more workers multiply the memory leak rather than dilute it, and a 60 s Redis cache leaves every miss blocking the event loop exactly as now.
2. Confirm the diagnosis before editing: `EXPLAIN (ANALYZE, BUFFERS)` the slow query with org 4127 and the 30 d bound, and record p50/p95 from Datadog plus pod RSS slope as the baseline you will re-check after each change.
3. No index serves this query — `events` has indexes only on `actor_id` and `kind`, so filtering org_id over 4.2M rows is a sequential scan; add `events (org_id, created_at DESC)` and expect the 1.2-1.6 s to drop to single-digit ms for 1,912 matching rows.
4. The pager is a blocking call in async code — `lookup_geo` uses `requests.get` (2 s timeout) inside an `async def` handler, so every cache-miss event stalls the whole worker's event loop, which is why `/healthz` misses the 3 s liveness probe; switch to an async HTTP client, or resolve geo out of band and store it on the event row.
5. Serialization is N+1 — `serialize_event` issues one `SELECT ... FROM users` per event, so limit=1000 means 1,000 round trips per request; fetch the distinct actor_ids in one `WHERE id = ANY($1)` query (or join users into the events query) and look up from a dict.
6. Dedupe is O(n²) — `seen` is a list and `ev["dedupe_key"] in seen` is a linear scan per row; make it a `set`.
7. The query has no LIMIT — it loads and deserializes every row in the window (including the `payload` JSONB) and then throws away all but `limit`; push dedupe and limit into SQL with `DISTINCT ON (dedupe_key)` ordered newest-first plus `LIMIT`, and keep the same "newest wins" semantics.
8. `_request_timings` grows forever — the timing middleware appends one float per request on *every* route at ~120 req/s, so ~8.6M entries accumulate in 20 h; replace with a bounded `collections.deque(maxlen=N)` or a fixed-bucket histogram.
9. `_geo_cache` also grows forever — keyed on raw client IP with no eviction and no bound; give it an LRU with a size cap.
10. Attribute the remaining RSS before calling the leak fixed — run `tracemalloc` (or `pympler`) on a pod for an hour; the two unbounded structures should account for most of the 310 MB → 2.1 GB climb, and if they don't, something else is retaining.
11. `/internal/metrics` sorts the entire timings list on every call, which is both a CPU spike and, on the event loop, another source of the healthz stalls — the bounded structure in step 8 fixes this too.
12. Re-run the step 2 baseline after each change, one change at a time, and revert anything that doesn't move the number.
13. Only after 3-7 land, revisit pool sizing with measured concurrency — a modest bump (e.g. max 10 → 20 at 4 workers) may be justified, 16×50 is not.
14. Keep `limit=1000` supported but tell the mobile team it's fetching 1,000 items to render a feed; a page size of 50 with a cursor would make this route boring regardless of org size.
