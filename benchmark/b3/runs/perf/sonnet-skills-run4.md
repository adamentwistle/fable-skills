1. Don't ship the on-call proposal as-is — it doesn't touch the root causes and the pool math is dangerous.
2. Root cause of the 1.2-1.6s DB time: `events` has no index on `(org_id, created_at)`, so the query is a sequential scan over all 4.2M rows for every call — add a composite index `events(org_id, created_at DESC)`.
3. Root cause of the remaining 5-10s and of the healthz outage: `lookup_geo` uses synchronous `requests.get`, called once per event serially inside `serialize_event`, blocking the whole asyncio event loop thread for up to 2s per uncached IP — this is why `/healthz` on that worker goes unresponsive and gets probe-restarted. Fix: use an async HTTP client (httpx.AsyncClient) or move the call off the event loop.
4. N+1 query: `serialize_event` does one `SELECT ... FROM users` per event, sequentially awaited — batch this into a single `WHERE id = ANY($1)` (or join) before serializing.
5. The query has no `LIMIT` and no server-side dedupe — it pulls the full 30-day window (1.9k rows for acme, more for bigger orgs) into Python every time, then dedupes with `if key in seen` on a plain list, which is O(n²), before finally slicing to `limit`. Fix with `DISTINCT ON (dedupe_key) ... ORDER BY dedupe_key, created_at DESC` wrapped in an outer `ORDER BY created_at DESC LIMIT $3`, pushing both dedupe and limit into SQL.
6. Root cause of the memory leak: `_geo_cache` is an unbounded dict keyed by IP, never evicted, growing forever — bound it (LRU with a max size, or a TTL) or move geo lookups to Redis/a real cache.
7. Secondary leak: `_request_timings` is appended to on every request and never trimmed — cap it (ring buffer / reservoir) or replace with a proper histogram.
8. Before touching pool size: check Postgres `max_connections`. 16 workers × pool max 50 × 6 pods = up to 4,800 connections — that alone can take down Postgres; if pool size changes at all, size it against `max_connections` and expected pod count, not guessed.
9. The proposed Redis cache key `(org_id, since, limit)` is close to useless for the actual traffic: the mobile client never sends `since`, so the handler computes it as `now() - 30d` fresh on every call (sub-second precision) — almost never a cache hit. If you still want a response cache, normalize `since` (e.g. floor to the minute, or treat "no since" as its own bucket) before keying on it.
10. After the index + batching + async geo fix, re-run: `EXPLAIN ANALYZE` the events query for org 4127, and re-measure endpoint p95 via the same Datadog view, plus RSS over a few hours to confirm the leak is actually gone before considering any worker/pool bump at all.
