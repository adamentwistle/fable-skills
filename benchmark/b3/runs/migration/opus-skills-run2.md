1. The backfill's `OFFSET` pagination walks a result set that shrinks as it writes, so it skips roughly every other batch — staging's own log proves it: 2,104,377 rows to do, "done: 1055000", i.e. ~50% silently left NULL; switch to keyset pagination (`WHERE state IS NULL AND id > :last_id ORDER BY id LIMIT 5000`).
2. `done += BATCH` counts intended rows, not written ones, so that "1055000" is fabricated and would have hidden the miss even at 0%; count `cur.rowcount` per batch.
3. The whole loop runs inside one `conn.transaction()` — not batched, not resumable, and on 61M rows it holds locks and generates WAL for the entire run; commit per batch.
4. That single transaction is also the replica risk: one 61M-row write burst will push the two streaming read replicas into heavy lag; per-batch commits plus a sleep/lag check between batches.
5. `OFFSET` cost is quadratic and staging already shows it (first 100k in 31s, the tenth 100k in ~110s); scaling total rows scanned (n²/2·BATCH) from staging's 440M-in-660s to prod's ~377B puts a correct run at roughly 6 days, not 11 minutes — keyset pagination removes this, and the fixed script must be re-timed before anyone commits to a window.
6. The `CASE` maps five spellings; prod holds 7,764 rows it doesn't cover (`PAID` 5,210, `canceled` 1,988, `complete` 417, NULL 149), which get `state = NULL`, so 0143's `SET NOT NULL` fails — add `upper(trim(status))` normalisation plus explicit handling for `complete` and NULL.
7. `complete` has no `OrderState` member and NULL has no obvious target; get a product decision on both before writing the mapping, and make the mapping `ELSE` raise rather than silently produce NULL.
8. "Safe to re-run" is false for those 7,764 rows — they stay `state IS NULL` forever and every re-run rewrites NULL over them; the `ELSE` guard in (7) makes re-runs actually converge.
9. `jobs/nightly_finance_export.py` still selects and filters on `orders.status` and breaks at 0143 — the grep was scoped to `app/` only; re-grep the whole repo (and any other service or ETL against this database) and switch that job to `state` in the expand phase.
10. That breakage lands at 02:00 UTC Friday, silently, in Finance's Looker model; confirm with Finance and cut the export over before 0143, not after.
11. Rollout order is wrong: step 2 deploys code whose `Order.from_row` calls `OrderState(row["state"])` on 61M rows where `state` is still NULL, so every order read raises immediately — deploy dual-write/read-old code first, backfill, then deploy read-new.

During the ~6 min rolling deploy the two pod versions disagree: new pods insert with `state` and no `status`, old pods' `mark_paid` matches `status = 'pending'` and updates nothing, and the webhook still returns 2xx — so paid orders stay pending with no retry; dual-write both columns for the whole expand phase.
13. Verify whether `orders.status` is NOT NULL — if it is, the new pods' INSERT fails outright the moment step 2 starts; I could not confirm this from the diff.
14. `ALTER COLUMN state SET NOT NULL` in 0143 takes ACCESS EXCLUSIVE and full-scans 61M rows, blocking all traffic for minutes; add a `CHECK (state IS NOT NULL) NOT VALID`, `VALIDATE CONSTRAINT`, then `SET NOT NULL` (PG12+ skips the scan).
15. 0143's downgrade recreates `status` empty — the data is gone, so there is no rollback after step 4; take a before-image (`id, status` to a side table or export) and keep `status` for days, not minutes.
16. 0143's downgrade also rebuilds `ix_orders_status` non-concurrently on 61M rows, locking the table during what is supposed to be a recovery; use `CONCURRENTLY` in an autocommit block, as 0142 does for the new index.
17. 0142 builds `ix_orders_state` before the backfill, so every backfilled row also writes an index entry; create the index after the backfill instead, and if `CONCURRENTLY` fails it leaves an INVALID index — the retry must drop it first.
18. The script has no dry-run mode; add one that reports the would-change count and sample IDs per spelling, and compare it against the GROUP BY before any real run.
19. Before rollout: run the fixed script end-to-end against a prod-sized restore, and record the real duration — the 11-minute figure describes a run that did half the work on 3% of the data.
20. Before rollout: run `alembic upgrade 0142 → downgrade → upgrade` locally against a database seeded with the messy spellings, not a fresh schema; the down path has never executed.
21. Between backfill and 0143: re-run the backfill as a final sweep and assert `SELECT count(*) FROM orders WHERE state IS NULL` is 0, and that migrated + remaining + errored equals the 61,437,902 before-count.
22. After 0143: spot-check ~10 known IDs (one per original spelling, including a former `PAID` and `complete`) through the real API read path, not just SQL, and watch order error rates and replica lag for the first hour.

It cannot ship Thursday. The backfill as written migrates about half the rows and would take days rather than minutes at prod scale, 0143 would fail on 7,764 unmapped rows, an unlisted reader (`jobs/nightly_finance_export.py`) breaks, and the step order makes every order read raise for the entire gap between deploy and backfill.
