1. Do not ship the on-call proposal. 16 workers × pool max 50 × 6 pods = 4,800 Postgres connections (default max_connections is 100–500), more workers multiplies the per-worker memory leak rather than fixing it, and neither change touches the blocking call that stops /healthz.
2. The Redis part is also near-useless as specified: `since` defaults to `now() - 30d`, so the resolved cache key is different on every request and hits ~0%; and a 60 s cache still lets the first miss block the worker for seconds.
3. Baseline before editing: `EXPLAIN (ANALYZE, BUFFERS)` the events SELECT with acme's params ($1=4127, 30 d), and time the endpoint 5× warm against acme — record median and spread; re-run both after every change below.
4. No index serves this query — `events` has indexes only on `actor_id` and `kind`, so filtering 4.2M rows by `org_id` + `created_at` is a scan plus sort; add `CREATE INDEX CONCURRENTLY events_org_created_idx ON events (org_id, created_at DESC)`. Expect the 1.2–1.6 s to drop to single-digit ms for 1,912 matching rows.
5. `serialize_event` issues one `SELECT ... FROM users WHERE id = $1` per event — 1,000 sequential round trips on one pooled connection; fetch all actors once with `WHERE id = ANY($1)` and build a dict.
6. `lookup_geo` calls blocking `requests.get` (2 s timeout) inside the async handler, freezing the whole worker's event loop — this, not the query, is why /healthz misses the 3 s liveness probe and pods restart; switch to `httpx.AsyncClient` (or `run_in_executor`) and cap concurrent lookups.
7. Dedupe uses `if ev["dedupe_key"] in seen` against a list — O(n²), ~1.8M comparisons at 1,912 rows and quadratic as orgs grow; use a `set` for membership and keep the list only for order.
8. The query has no `LIMIT` — every request materializes the full 30 d window before Python slices to `limit`; push it into SQL as `SELECT DISTINCT ON (dedupe_key) ... ORDER BY dedupe_key, created_at DESC` wrapped in an outer `ORDER BY created_at DESC LIMIT $3`, preserving newest-wins.
9. `_request_timings` grows forever, one float per request across all routes — at 120 req/s that is ~8.6M entries in 20 h and is the bulk of the 310 MB → 2.1 GB climb; replace with a bounded `deque(maxlen=...)` or a fixed-bucket histogram.
10. `_geo_cache` is an unbounded dict keyed by client IP with no eviction — a second, slower leak; bound it (TTL or LRU with a max size).
11. `/internal/metrics` sorts the entire timings list on every call — O(n log n) on millions of floats, blocking the loop; the bounded structure from step 9 fixes this too.
12. Re-run step 3's measurements plus the correctness suite, specifically that dedupe still keeps the newest row per `dedupe_key` and ordering is unchanged, then confirm pod RSS is flat over a few hours before closing.
13. Optional stopgap only while the above lands: give the liveness probe a longer timeout or a separate port — do not treat it as the fix.
14. Follow-up for the mobile team: `limit=1000` per load is the wrong shape; keyset pagination on `(created_at, id)` with a page of ~50 is the durable answer.
