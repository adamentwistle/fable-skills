1. `MAPPING` CASE has no ELSE — prod's `PAID`, `canceled` (single-L), `complete`, and null status (7,764 rows total, per the prod GROUP BY) map to `state = NULL` and never converge on any re-run — add an ELSE/explicit handling (with a decision on what `complete` becomes) instead of silently leaving them NULL.
2. `Order.from_row` does `OrderState(row["state"])` with no NULL tolerance, and step 2 (app deploy) runs before step 3 (backfill) — every one of the 61.4M rows has `state = NULL` right after deploy, so every order read raises `ValueError` until the backfill catches up — reorder to expand/migrate/contract: deploy code that falls back to `status` when `state` is NULL, backfill, verify, only then cut reads over.
3. `mark_paid`'s `WHERE state = $3` (PENDING) will match 0 rows for any order still NULL/unbackfilled, so the payment webhook returns 2xx while the order silently never flips to paid — until the cutover is safe, match on `status='pending' OR state=0` too.
4. Backfill script wraps the whole batch loop in one `conn.transaction()` — it isn't actually committing per batch, so a killed/OOM'd job rolls back all progress and holds long-running row locks the whole time — commit each batch separately.
5. Backfill uses `OFFSET` against a `state IS NULL` set that shrinks as it updates — this skips roughly every other batch; staging's own log proves it (`1,055,000` updated out of `2,104,377` reported, half the total) — replace with a stable cursor (e.g. `id > last_id`) instead of `OFFSET`.
6. `jobs/nightly_finance_export.py` (under `jobs/`, outside the `app/`-scoped grep) still selects `o.status` — it breaks the first time it runs after 0143 drops the column, and it runs nightly at 02:00 UTC — fix/gate this reader before 0143 ships, it was missed, not "not a reader."
7. No dry-run/count-reconciliation step in the backfill — add one that reports counts per status (mapped vs. unmapped) against the known prod GROUP BY before running for real.
8. Staging is 2.1M rows vs. prod's 61.4M (29x), and the one staging run didn't even finish cleanly (see #5) — prod timing and lock behavior are unverified at scale — test against a prod-sized snapshot before Thursday.
9. `alter_column("orders", "state", nullable=False)` in 0143 takes an ACCESS EXCLUSIVE lock for a full-table verification scan on 61M rows — use a `NOT VALID` CHECK + `VALIDATE CONSTRAINT` first to shrink the lock window, or run at low traffic with a `lock_timeout`+retry.
10. No rollback plan is stated for 0143 failing mid-window — which #1 guarantees will happen (NOT NULL alter hits the permanently-NULL rows) — write one now (e.g. hold 0143, ship only 0142+backfill Thursday, land 0143 later once the unmapped rows are resolved).
11. 0143's `downgrade()` recreates `status` as empty nullable text with no data restored from `state` — rollback loses status history for anything written state-only after cutover — note this explicitly as a one-way step once taken, don't rely on `alembic downgrade` as a real rollback.
