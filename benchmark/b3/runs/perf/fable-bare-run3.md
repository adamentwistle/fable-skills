Do not ship the proposal: 16 workers × 50 conns × 6 pods = 4,800 Postgres connections (will hit max_connections and slow every route), and the Redis key includes `since`, which defaults to `now()-30d` at microsecond precision, so the mobile client would never get a cache hit; neither change touches the leak or the probe restarts.
2. Root cause of the probe restarts: `lookup_geo` uses blocking `requests.get` inside an async handler, so every cache miss (up to 1,000 per request, 2 s timeout each) freezes the worker's event loop and `/healthz` with it; switch to `httpx.AsyncClient` with a bounded `asyncio.gather` (semaphore ~20), or better, resolve geo at ingest and store city/country on the event.
3. Root cause of the RSS growth: `_request_timings` is an unbounded list appended on every request on every route (~8.6M floats per pod per 20 h) and `_geo_cache` is an unbounded dict; replace timings with `collections.deque(maxlen=10000)` under the same name (metrics.py keeps working) and make the geo cache a `cachetools.TTLCache`.
4. `/internal/metrics` does `sorted()` on that whole list on the event loop each scrape, so scrapes also block `/healthz`; the deque cap fixes it, but long term push a histogram to Datadog instead of per-worker in-process stats (the current numbers are per-worker, not per-pod, anyway).
5. Confirm with `EXPLAIN (ANALYZE, BUFFERS)` on the logged query, then `CREATE INDEX CONCURRENTLY events_org_created_idx ON events (org_id, created_at DESC)`; there is no index covering `org_id`, so the 1.2-1.6 s is a seq scan of 4.2M rows to find 1.9k. This is safe to run today and needs no deploy.
6. N+1: `serialize_event` runs one `users` query per event, sequentially awaited, so ~1,000 round trips per request; fetch all actors once with `WHERE id = ANY($1)` and map in memory.
7. Dedupe uses a `list` for `seen`, so membership is O(n²); move dedupe into SQL (`DISTINCT ON (dedupe_key)` in a subquery, then `ORDER BY created_at DESC LIMIT $3`) so the query returns at most `limit` rows and stops shipping every row and its JSONB payload for the window.
8. No SQL `LIMIT` and no lower bound on `since`: a client sending `since=1970-01-01` pulls the org's entire history into memory; the SQL LIMIT in step 7 plus clamping `since` to a max window fixes both.
9. The pool connection from `Depends(get_conn)` is held for the whole request, including the geo HTTP calls, so one slow request pins a connection for 6-12 s; after steps 2 and 6 the connection is only needed for two short queries, so release it before serialization.
10. Deploy steps 2-9 as one change, then verify: p95 for acme should drop to under 300 ms, `/healthz` should stay under 50 ms during a limit=1000 request, and pod RSS should be flat over 24 h with zero liveness restarts.
11. Follow-up, not today: add `UNIQUE (org_id, dedupe_key)` on events with `ON CONFLICT DO NOTHING` at the webhook ingest so duplicates never land and read-time dedupe can be deleted.
12. Do not raise the liveness probe timeout or the memory limit to hide this; both would just delay the same restarts.
