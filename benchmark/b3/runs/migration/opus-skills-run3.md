**This cannot ship Thursday.** The backfill silently migrated only half the rows on staging and would leave ~7,764 prod rows permanently NULL; step 4 would fail or take the table down, and the nightly finance export breaks. Re-plan as two releases.

1. The backfill skips half the table: it pages with `OFFSET` over the same `state IS NULL` predicate it is updating, so each batch's update shifts the remaining rows under the next offset — fix by dropping `OFFSET` and looping `WHERE state IS NULL ORDER BY id LIMIT 5000` (or keyset on `id > last_id`).
2. Staging already showed this and it was read as success: 2,104,377 rows in, "done: 1055000" out — that is the every-other-batch signature, and ~1.05M staging rows are still unmigrated right now; fix by re-running the corrected script on staging and asserting zero NULLs.
3. `done` is a lie regardless — it adds `BATCH` per iteration and ignores `cur.rowcount`, so the log cannot detect the above; fix by accumulating `cur.rowcount`.
4. The `CASE` has no `ELSE`, so `PAID` (5,210), `canceled` (1,988), `complete` (417) and NULL (149) map to NULL and stay NULL forever because the script's own filter is `state IS NULL`; fix by normalizing case, mapping `canceled`→3, and deciding explicitly on `complete` and NULL before running.
5. `complete` has no `OrderState` member at all — fix by adding a state or agreeing a target value with whoever writes it, and grep for the writer, since something is still producing it.
6. Rollout order breaks reads: step 2 deploys code whose `from_row` does `OrderState(row["state"])` while nearly every row is NULL, so every fetch of a pre-existing order raises for the whole gap until step 3 finishes — fix by backfilling before deploying, and having `from_row` fall back to `status` during the expand phase.
7. Money bug in the same gap: `mark_paid` matches `state = 0`, a not-yet-backfilled pending order has `state IS NULL`, the UPDATE hits 0 rows and the webhook still returns 2xx, so the provider never retries and the payment is lost — fix by matching `(state = $3 OR status = 'pending')` until contract, or by backfilling first.
8. Nothing dual-writes: old pods insert `status='pending'` with `state` NULL for the ~6 min rolling deploy, after the backfill's snapshot — fix by writing both columns in the expand release.
9. `jobs/nightly_finance_export.py` reads `orders.status` and was missed because the grep was scoped to `app/`; it runs 02:00 UTC and feeds Finance's Looker model, so it breaks the morning after 0143 — fix by updating it to `state IN (1,2)` and re-grepping `status` across the whole repo, not `app/`.
10. Timing does not fit the window: 61,437,902 rows is 29× staging, and staging's own numbers degrade (100k at 31s, 1M at 627s — the quadratic `OFFSET` scan), so a corrected full run is roughly 5–11 hours at staging's observed 1,600–3,200 rows/s, not 11 minutes; fix by running the backfill out of band, days ahead, not inside a deploy window.
11. The entire loop is inside one `conn.transaction()` — not batched, not resumable, one 61M-row transaction holding locks and bloating the table; fix by committing per batch.
12. `ALTER COLUMN ... SET NOT NULL` in 0143 takes ACCESS EXCLUSIVE and full-scans 61M rows; fix with `ADD CONSTRAINT ... CHECK (state IS NOT NULL) NOT VALID`, then `VALIDATE CONSTRAINT`, then `SET NOT NULL`.
13. 0143 has no rollback: its downgrade recreates `status` empty, so the original strings are gone and reverting the app deploy leaves code reading a dropped column; fix by snapshotting `(id, status)` to a side table before the drop.
14. Expand and contract are minutes apart in one window, which is the entire failure mode the sequence exists to prevent; fix by shipping 0142 + backfill + app in release 2026.36 and 0143 no earlier than 2026.37.
15. The index is created in 0142 before the backfill, so all 61M updates also write the index; fix by creating `ix_orders_state` concurrently after the backfill.
16. 0142's downgrade drops the index non-concurrently and will not clean up an INVALID index left by a failed `CREATE INDEX CONCURRENTLY`; fix with `DROP INDEX CONCURRENTLY IF EXISTS`.
17. 61M row updates will spike WAL and lag both read replicas, so replica reads return stale/NULL `state` mid-run; fix by throttling batches on a `pg_stat_replication` lag check.
18. The script has no dry-run mode; fix by adding one that prints per-target-value counts and sample IDs without writing.
