1. Do not ship the on-call proposal — item 1 gives 16 workers × 50 conns × 6 pods = 4,800 Postgres connections (past any sane `max_connections`) and multiplies the per-worker memory leak by 4; item 2 never hits, because `since` defaults to `datetime.now()` so every cache key is unique.
2. Baseline first: `EXPLAIN (ANALYZE, BUFFERS)` the events SELECT for org 4127, and time the endpoint 5× warm against acme's 1,912-event window, so every change below is judged by the same two numbers.
3. Missing index — `events` has indexes on `actor_id` and `kind` only, so the query seq-scans all 4,213,660 rows to return 1,912; add `CREATE INDEX CONCURRENTLY events_org_created_idx ON events (org_id, created_at DESC)`.
4. Query fetches the whole 30-day window and slices in Python — push `LIMIT` into SQL, and because the limit must apply after dedupe, do the dedupe in SQL too (`DISTINCT ON (dedupe_key) ... ORDER BY dedupe_key, created_at DESC` in a subquery, re-sorted by `created_at DESC`).
5. Dedupe loop is O(n²) — `seen` is a list, so `ev["dedupe_key"] in seen` is a linear scan, ~1.8M comparisons at 1,912 rows; if any Python-side dedupe survives step 4, make `seen` a `set`.
6. N+1 query — `serialize_event` runs one `SELECT ... FROM users` per event, 1,912 sequential round trips per request; fetch all actors in one `WHERE id = ANY($1)` and build an id→user dict, or join `users` into the events query.
7. Blocking call in the async path — `requests.get` in `lookup_geo` is synchronous and stalls the whole worker's event loop for up to 2 s per uncached IP, which is why `/healthz` stops answering and the 3 s liveness probe has killed pods 14 times; switch to an async client (`httpx.AsyncClient`, shared) and gather the lookups, or drop geo from this route.
8. Geo lookups are also serial and unbounded in count — cap total per request and fail soft (return `location: null` on timeout) rather than letting one slow GeoIP call decide the endpoint's p95.
9. Memory leak, primary — `_request_timings` grows forever for *every* request on every route: 120 req/s × 20 h ≈ 8.6M floats per worker, which matches RSS climbing 310 MB → 2.1 GB over ~20 h; replace with a bounded `collections.deque(maxlen=...)` or running counters.
10. Memory leak, secondary — `_geo_cache` is an unbounded dict keyed on client IP with no eviction; bound it (`functools.lru_cache` or a size-capped dict with TTL).
11. `/internal/metrics` sorts the entire timings list on each call — O(n log n) over millions of entries, synchronously, blocking the loop; fixed by the deque in step 9, or keep a histogram instead of raw samples.
12. Re-run the step-2 measurement after each of steps 3, 4, 6, 7 separately, and revert any change that does not move the number.
13. Verify correctness after: same events, same order, same dedupe winner (newest per `dedupe_key`) as the current code, and add `id DESC` as a tiebreaker to `ORDER BY created_at DESC` so equal timestamps do not reorder between calls.
14. Only after the above, revisit capacity — with the index and the N+1 gone this route should be tens of milliseconds, so the worker and pool bumps are almost certainly unnecessary; if you still want a Redis cache, key it on a rounded `since` bucket, not the raw timestamp.
