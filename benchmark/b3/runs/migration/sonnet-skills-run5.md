1. Mapping only handles 5 lowercase strings; prod has `PAID`(5210), `canceled`(1988), `complete`(417), and NULL(149) — those ~7.8k rows get `state=NULL` — normalize case/spelling and add an explicit branch (or hard-fail) for every distinct value instead of falling through to NULL.
2. Staging's own log shows only 1,055,000/2,104,377 rows updated (50%) — the OFFSET-based pagination shifts as rows leave the `WHERE state IS NULL` set on each UPDATE, so every other batch is skipped — paginate by `WHERE id > :last_id ORDER BY id LIMIT` instead of OFFSET.
3. The whole backfill runs inside one `with conn.transaction()` — nothing commits until the full run finishes, so "safe to re-run" is false on a mid-run crash (all progress lost) — commit per batch.
4. One multi-hour transaction on the primary holds back autovacuum/WAL cleanup on a 61M-row hot table — same per-batch-commit fix as #3 bounds this.
5. The `status` grep was scoped to `app/` and missed `jobs/nightly_finance_export.py`, which selects `o.status` and filters on it — it breaks outright once 0143 drops the column, and silently undercounts paid/shipped orders created between the app deploy and 0143 — add it to the reader inventory and convert it to `state` before 0143 runs.
6. Staging throughput doesn't project cleanly to prod scale: even at the (buggy) observed rate, ~61.4M rows extrapolates to roughly 10-11 hours once the OFFSET bug is fixed to actually cover every row — that doesn't fit inside a same-day rollout window.
7. `ALTER COLUMN state SET NOT NULL` on 61M rows takes an ACCESS EXCLUSIVE lock for a full-table validation scan on Postgres 15, blocking all reads/writes on `orders` — do it via `ADD CONSTRAINT ... CHECK (state IS NOT NULL) NOT VALID` + `VALIDATE CONSTRAINT` (concurrent-safe) before the NOT NULL alter.
8. (Between backfill and 0143) No reconciliation gate exists — require `SELECT count(*) FROM orders WHERE state IS NULL` = 0 and a spot-check of mapped values against `status` before running 0143, on a separate day, not back-to-back in the same window.
9. 0143 drops `status` with no backup of the pre-migration values, including the anomalous 7.8k rows from #1 — export/archive the column before dropping so there's an actual rollback path.
