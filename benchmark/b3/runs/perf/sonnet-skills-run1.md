1. Do not ship the proposal as-is: bigger pools and a Redis cache paper over an O(n²) dedupe bug and a memory/liveness bug without fixing either.
2. Root cause of latency: no index on (org_id, created_at) — the query does a full scan/sort of 4.2M rows every call; add `CREATE INDEX events_org_id_created_at_idx ON events (org_id, created_at DESC)`.
3. Root cause of "6-12s for ~1.9k events": `serialize_event` does one `SELECT ... FROM users` per row, sequentially awaited — that's 1,900+ round trips (N+1); batch with one `SELECT id, display_name, avatar_url FROM users WHERE id = ANY($1)` and build a dict.
4. `seen: list[str]` + `if ev["dedupe_key"] in seen` is O(n²) dedupe over up to thousands of rows; make `seen` a `set`.
5. Query has no `LIMIT` — it fetches and dedupes the entire 30-day window from Postgres, then truncates to `limit` in Python; push `ORDER BY created_at DESC LIMIT` (with enough headroom for dedupe, or dedupe in SQL via `DISTINCT ON (dedupe_key)`) down to the database.
6. `lookup_geo` makes a **synchronous** `requests.get` call inside an async endpoint — this blocks the entire event loop for that worker, which is why `/healthz` stops responding and the liveness probe kills the pod; this is the actual cause of the restarts, not pool size. Fix: use an async HTTP client (e.g. httpx.AsyncClient) or move geo lookup off the request path.
7. `_geo_cache: dict[str, dict]` is a module-level dict with no eviction — it grows one entry per unique IP forever; that's the RSS climb to 2.1GB/20h. Bound it (LRU/TTL cache) or drop it in favor of a real cache (Redis) with expiry.
8. `_request_timings: list[float]` also grows unbounded for the life of the process — same leak pattern, feeds into the same OOM; cap it (ring buffer) even though metrics.py reads it.
9. `events_actor_id_idx` and `events_kind_idx` are unused by this query and irrelevant to the fix; don't add more indexes than #2.
10. Once #2–#6 land, re-measure: expect the query to drop from ~1.4s to low-ms and the N+1 to disappear, which should bring p95 for acme-sized orgs down to well under 1s without touching worker/pool counts.
11. Only after that, consider raising uvicorn workers/pool size if CPU-bound headroom is still needed — bumping to 16/50 now would mainly let more blocked-event-loop requests pile up concurrently, hiding the real bug and increasing DB connection pressure (6 pods × 16 workers × 50 = 4800 potential connections).
12. Response caching (Redis, 60s) is reasonable as a later optimization for hot orgs, not as the fix — cache a correctly-fixed response, not a slow one, and it doesn't address the event-loop-blocking bug at all.
