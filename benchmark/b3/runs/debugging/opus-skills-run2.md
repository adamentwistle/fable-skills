Root cause: the cache has no invalidation — `_cache` is populated once and nothing ever compares it against the file's current state, so the only thing that clears it is process exit; fix by storing the file's identity alongside the value (`os.stat(path)` → `st_mtime_ns` + `st_size`, plus the resolved path) and re-reading when that tuple changes.
2. The cache also ignores `path` — the first call wins and a later `get_config('other.json')` returns the wrong file's contents; fix by keying the cache dict on the resolved absolute path.
3. The cached `dict` is returned by reference, so any caller mutating it silently rewrites everyone's config and can hide the staleness bug; fix by returning a deep copy, or freezing the loaded structure.
4. NOT a fix — a TTL / time-based expiry: it shortens the stale window but still serves known-wrong values for the whole interval, and picks an arbitrary number instead of a correct condition.
5. NOT a fix — an explicit `reload_config()` or `_cache = None` at call sites: a mitigation that pushes correctness onto every caller and fails the moment one forgets; acceptable only as an addition to finding 1.
6. NOT a fix — changing `if _cache is None` to `if not _cache`: no effect on staleness, and it introduces a re-read-every-call bug for a legitimately empty `{}` config.
7. NOT a fix — deleting the cache entirely: correct but trades the bug for a JSON parse on every call; only take this if profiling shows the load is cheap and hot-path frequency is low.
8. NOT a fix — adding a lock: addresses concurrent double-load, not staleness; still needed *after* finding 1, since stat-then-read-then-store is a race.
9. Reproduction and verification (run before and after): call `get_config()`, write a changed value to `config.json`, call again in the same process, assert the two returned values differ — and repeat the write twice inside one second to confirm the invalidation survives coarse mtime resolution, which is why the check must use `st_mtime_ns` + `st_size` rather than `st_mtime`.
10. Residual risk if the config is written by a non-atomic writer or lives on a filesystem with coarse timestamps (FAT, some network mounts): same-size same-timestamp edits go undetected; fall back to hashing the file contents if that applies.
