1. `services/notifier/src/reminders.ts:57` and `scripts/backfill-late-fees.js:22` still call `computeLateFee` with the old `(invoice, graceDays)` positional number, but the new signature reads `opts.graceDays` — `opts` will be a number, `opts.graceDays` is `undefined`, `overdue` becomes `NaN`, and every fee computed by the notifier and the backfill script silently becomes `NaN`/0. Turbo's `--filter='[origin/main]'` skipped both packages ("no changes since origin/main"), so CI never ran them — this is a hard blocker, not covered by "CI is green."
2. Same two call sites also still read `cfg.INVOICE_GRACE_DAYS`, which no longer exists in `ConfigSchema` (renamed to `BILLING_GRACE_PERIOD_DAYS`) — `graceDays`/env value is `undefined` there too, compounding finding 1. Update both call sites to the new options-object + new config key before merge.
3. `infra/helm/billing/values.prod.yaml:31` and `values.staging.yaml:29` still set `INVOICE_GRACE_DAYS`, which `loadConfig` no longer recognizes — Zod will apply the new `BILLING_GRACE_PERIOD_DAYS` default (7) in every environment, silently cutting prod grace period from 21 days to 7 on deploy. Update the Helm values (and `docs/runbooks/dunning.md:18`, which still references the old var name) in the same change.
4. `total_cents`/`currency` → `total: {amount, currency}` and `"paid"` → `"settled"` is a breaking response-shape and enum-value change on `GET /v1/invoices/:id` and the `billing.invoice.updated` event (`events.ts` still calls `toInvoiceResponse` unchanged). The PR description's "platform team confirmed compatibility" is unverifiable from this diff and contradicted by the repo's own code: `apps/portal/src/client/hooks/useInvoice.ts:23` reads `data.total_cents`, `InvoiceBadge.tsx:9` checks `status === 'paid'`, and `services/reconciler/reconcile.py:64` checks `inv["status"] == "paid" and inv["total_cents"]` — all three break the instant this ships, and the reconciler package was skipped by CI's filter so nothing caught it. Block until these three consumers are updated or the API is versioned/dual-shaped.
5. `amount` changed from an integer cents field to a string decimal (`(inv.totalCents / 100).toFixed(2)`) — any consumer doing numeric math on `total.amount` gets string concatenation or NaN; this is a silent type change on top of the shape change, worth flagging to whoever migrates the consumers in finding 4.
6. `InvoiceState.Disputed` was inserted between `Open` and `Paid` in the enum, shifting the underlying numeric values of `Paid` (2→3) and `Void` (3→4). `repo.ts`'s `update({ state: InvoiceState.Paid, ... })` writes the new numeric value going forward, but `invoices.state` is a persisted SMALLINT column — every existing row written under the old enum now decodes to the wrong state. This is the classic "old data lives forever" break: needs a migration (or append `Disputed` at the end of the enum instead of the middle) before merge.

The test that would have caught finding 6 was disabled, not fixed: `invoice.test.ts` skips "round-trips state values through the invoices table" with a comment blaming a stale fixture DB, and the assertions in `serializes a paid invoice` were weakened from exact `status`/`total_cents`/`currency` checks to `toBeTruthy()`/`toBeDefined()` — the suite is green because the regression tests were gutted, not because behavior is correct. Restore real assertions and re-enable the state round-trip test before trusting "tests updated, suite green."
8. `computeLateFee`'s fee formula changed from a hardcoded 1.5%/30-days to `rateBps` driven, and the default (`150` bps = 1.5%) matches, but confirm this is intentional given the "quality only" note — flag as a behavior change worth a sentence in the PR description, not just a refactor.
