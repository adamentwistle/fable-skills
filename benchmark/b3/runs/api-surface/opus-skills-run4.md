**Block the merge.** Findings, most severe first.

1. **Enum renumbering corrupts persisted data** — inserting `Disputed` before `Paid` shifts `Paid` 2→3 and `Void` 3→4, and `invoices.state` is a SMALLINT storing those ordinals; every existing Paid row now reads as Disputed and every Void row as Paid. Fix: append `Disputed` last, or give the enum explicit values and ship a data migration for the shifted rows.
2. **The test that catches #1 was skipped, not fixed** — `round-trips state values through the invoices table` seeds `state: 2, 3` and asserts `[Paid, Void]`; it started failing *because* the change is wrong. Un-skip it; "flaky since the Disputed change" is the bug reporting itself.
3. **CI green is not evidence** — `--filter='[origin/main]'` skipped `@acme/notifier`, `@acme/reconciler-client` and `@acme/scripts`, which are exactly the packages that consume the changed API. Required: run typecheck+test across all dependents of `@acme/billing-core` before merge.
4. **`services/notifier/src/reminders.ts:57` is broken** — still calls `computeLateFee(inv, cfg.INVOICE_GRACE_DAYS)`; `opts.graceDays` is `undefined`, so `overdue` is `NaN`, the `<= 0` guard fails open and the fee is `NaN`. Update the call site to the options object.
5. **`scripts/backfill-late-fees.js:22` is broken the same way and is plain JS**, so no typecheck will ever catch it; it also reads the removed `INVOICE_GRACE_DAYS` env var. Update it and add it to a lint/test gate.
6. **Config rename silently reverts production grace to 7 days** — `infra/helm/billing/values.prod.yaml:31` sets `INVOICE_GRACE_DAYS: "21"` (staging 14); zod ignores the unknown key and defaults the new one, so prod goes 21→7 and starts charging late fees two weeks early. Ship the Helm value renames in the same change, or accept both keys with the old one deprecated.
7. **`docs/runbooks/dunning.md:18` documents `INVOICE_GRACE_DAYS` as the incident lever to pause late fees** — after the rename that lever is a no-op during an incident. Update the runbook in this PR.
8. **The reviewer note is contradicted by the author's own sweep** — `useInvoice.ts:23` reads `data.total_cents`, `InvoiceBadge.tsx:9` matches `status === 'paid'`, `reconcile.py:64` matches both. Get that compatibility claim in writing from the platform team with the shapes named, or treat it as false.
9. **Removing `total_cents` is a breaking wire change with a fail-open consumer** — `reconcile.py:64` compares `inv["total_cents"] == ledger_cents` *and* `status == "paid"`; after this both stop matching, so reconciliation silently passes on every invoice instead of erroring. Keep `total_cents` alongside the new `total` object and remove it in a later release.
10. **`paid` → `settled` is a breaking vocabulary change with no version** — same fix: emit both, or version the endpoint; the UI badge and the reconciler both key off the literal `paid`.
11. **`toInvoiceResponse` also serializes the `billing.invoice.updated` event** (`events.ts`), so this reshape hits every queue consumer, and already-queued messages carry the old shape. No event consumers were enumerated; enumerate them before merge.
12. **`total.amount` is a string, and `/100` assumes two minor units** — `(totalCents / 100).toFixed(2)` breaks for zero-decimal currencies like JPY. Keep integer minor units on the wire.
13. **Version bump is wrong** — `2.3.1` → `2.4.0` is a minor bump for a set of breaking changes; needs `3.0.0` plus a changelog entry and migration note.
14. **Route and dunning now compute different fees** — `invoiceRoutes.ts:88` omits `rateBps` and falls back to a hardcoded `150`, while dunning passes `config.LATE_FEE_RATE_BPS`; the displayed fee will diverge from the charged fee whenever that config differs from 150. Pass the config value in both, and drop the literal default in favor of the schema default.
15. **The serializer test was gutted, not updated** — `expect(res.status).toBeTruthy()` and `expect(res.total).toBeDefined()` would pass for any garbage. Assert the exact status string, amount and currency.
