1. Do not ship the proposal: 16 workers × 50 conns × 6 pods = 4,800 Postgres connections (default max is 100), more workers multiplies the per-worker leaks 4×, and the Redis key includes `since`, which for the mobile client is `now() - 30d` at microsecond precision, so it would never hit.
2. Today's mitigation only: raise the liveness probe timeout/failureThreshold (or point it at a TCP check) so the restart pages stop while the real fix lands; leave readiness as is.
3. Root cause of the /healthz stalls and restarts: `lookup_geo` calls blocking `requests.get` (2 s timeout) inside the async handler, up to 1,000 times per request, freezing the event loop for the whole worker; switch to `httpx.AsyncClient`, look up only the unique IPs per request with bounded concurrency, and degrade to `location: null` on error instead of failing the request.
4. Root cause of the 1.4 s query: no index on `(org_id, created_at)`, so every call seq-scans 4.2M rows; `CREATE INDEX CONCURRENTLY events_org_created_idx ON events (org_id, created_at DESC)` and confirm with `EXPLAIN ANALYZE`.
5. Query has no `LIMIT` and `since` is unclamped, so a client can pull an org's entire history into memory; push dedupe and limit into SQL (`DISTINCT ON (dedupe_key)` subquery, `ORDER BY created_at DESC, id DESC LIMIT $3`) and clamp `since` to a floor.
6. Dedupe uses a list for `seen`, so it's O(n²) per request; the SQL change removes it, otherwise make it a set.
7. N+1: one `users` fetchrow per event, awaited sequentially, is ~1,000 round trips per request and most of the gap between the 1.4 s query and the 6 s p50; fetch actors in one `WHERE id = ANY($1)` query (or join in the main select).
8. Memory leak #1: `_request_timings` grows forever (~30 req/s per worker ≈ 2M floats per worker per 20 h) and `/internal/metrics` sorts the whole list on every call, blocking the loop; replace with a bounded `deque(maxlen=...)` or a proper histogram.
9. Memory leak #2: `_geo_cache` is unbounded and per worker, so every unique client IP ever seen is held 4× per pod; replace with a size-capped TTL cache (or Redis if it must be shared).
10. Confirm the leak split before closing: expose `len(_geo_cache)` and `len(_request_timings)` temporarily, or run tracemalloc on one pod, then verify RSS is flat over 24 h after 8 and 9 ship.
11. Verify the fix under load: acme p95 under 0.5 s in Datadog, `/healthz` answers during a 1,000-event request, EXPLAIN shows an index scan, zero probe restarts for a week.
12. Revisit caching only after 3 to 9 land and only if the numbers still demand it; the pool and worker bump is not needed at all.
