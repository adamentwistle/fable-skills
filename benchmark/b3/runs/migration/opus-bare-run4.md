1. `OFFSET` paging over a predicate the loop itself shrinks (`state IS NULL`) skips rows — each committed batch pulls the remaining set left while the offset walks right; switch to keyset paging (`WHERE state IS NULL AND id > :last ORDER BY id LIMIT 5000`) with no OFFSET.

3. `done += BATCH` counts rows requested, not updated, so the completion number is fiction; accumulate `cur.rowcount`.
4. The whole loop is inside one `conn.transaction()`, so 61M rows sit in a single transaction — hours of held snapshot, table bloat, and nothing is durable until the end, which also makes "safe to re-run" false; commit per batch.
5. `CASE status` has no `ELSE`, so `PAID`, `canceled`, `complete` and the 149 NULLs map to NULL and stay NULL forever (7,764 rows); normalize with `lower(trim(status))` and map the variants explicitly.
