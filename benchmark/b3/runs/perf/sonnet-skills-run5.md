1. Don't ship the proposal as-is — it treats symptoms, not the two root causes (missing index, blocking event loop), and one part of it is dangerous, one part is broken.
2. Root cause of the 1.2-1.6s query: no index on `events(org_id, created_at)` — Postgres is scanning/sorting against 4.2M rows for every call regardless of org size. Add a composite index `(org_id, created_at DESC)`.
3. Root cause of `/healthz` freezing and the pod restarts: `lookup_geo` uses synchronous `requests.get` inside an `async def` handler, blocking the whole event loop (and every other request on that worker, including `/healthz`) for up to 2s per uncached IP. Switch to an async HTTP client (httpx.AsyncClient) or run it in a thread pool.
4. Root cause of the memory leak: `_geo_cache` is an unbounded dict that never evicts — this is what drives RSS from 310MB to 2.1GB over ~20h. Bound it (LRU/TTL/max size).
5. Secondary leak/growth: `_request_timings` is also appended to forever and never trimmed — bound it (ring buffer or reservoir), independent of the geo cache fix.
6. N+1 query: `serialize_event` does a per-row `SELECT ... FROM users` — for 1000 events that's 1000 round trips. Batch with one `WHERE id = ANY($1)` or a join.
7. Unbounded fetch + O(n²) dedupe: the SQL has no `LIMIT`, so it pulls every matching row before Python dedupes with `if ev["dedupe_key"] in seen` (list scan) and slices `[:limit]` afterward. Push dedupe+limit into SQL (e.g. `DISTINCT ON (dedupe_key) ... ORDER BY dedupe_key, created_at DESC` wrapped and re-sorted, or a window function) so at most `limit` rows come back and are processed.
8. On-call's worker/pool bump: reject — 16 workers × pool max 50 × 6 pods = up to 4,800 DB connections, which will exhaust Postgres `max_connections` and take down other services; it also multiplies the per-worker leak rate, so pods will OOM faster, not less often.
9. On-call's Redis cache: reject as specified — `since` defaults to `datetime.now(timezone.utc) - 30d` computed fresh per request, so the cache key is different on almost every call and will essentially never hit. If you still want it after the fixes above, bucket `since` (round to the minute) before using it as a key, and only add it once the endpoint itself is fast — caching a slow response just hides p95 for repeat calls inside 60s.
10. After 2–7 land, re-measure p50/p95 for acme and northwind before deciding whether workers/pool size need to move at all.
