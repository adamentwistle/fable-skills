1. Reject both halves of the proposal as-is — they mask root causes and the pool math is dangerous: 16 workers × 50 conns × 6 pods = 4,800 asyncpg connections against a Postgres instance that almost certainly caps at ~100-300 `max_connections`; shipping it as written will take the DB down.
2. Root cause of the healthz outages/restarts: `lookup_geo()` calls blocking `requests.get()` inside an async handler, so one uncached IP freezes that worker's entire event loop, including `/healthz` — fix: swap to an async client (`httpx.AsyncClient`) or run it in a thread executor.
3. Root cause of the RSS growth to 2.1 GB: `_geo_cache` and `_request_timings` are unbounded module-level containers that never evict — fix: cap/TTL the geo cache (LRU with maxsize) and cap or periodically rotate `_request_timings`.
4. Root cause of the 1.2-1.6 s query time: no index covers `(org_id, created_at)`, so Postgres scans against 4.2M rows every call — fix: `CREATE INDEX events_org_created_idx ON events (org_id, created_at DESC)`.
5. Root cause of the rest of the per-request latency: `serialize_event` issues one sequential `SELECT` per event for the actor (~1,900 round trips for acme) — fix: batch-fetch actors once with `WHERE id = ANY($1)` and look up from a dict.
6. Query fetches and dedupes the full 30-day window in Python before applying `limit` — fix: dedupe with a `set` (current `dedupe_key in list` is O(n²)) and push `LIMIT` into SQL once the actor lookup is batched.
7. `conn` is held for the whole request, including the blocking geo call — this pool-exhaustion pressure mostly disappears once #2 and #5 are fixed, so don't separately "fix" it by just adding more connections.
8. Re-measure latency/memory/pod stability after 2-6 before touching worker or pool counts at all.
9. Only after that, a short (30-60 s) Redis cache keyed on (org_id, since, limit) is a reasonable addition, not a substitute for the above — don't cache over an endpoint that's still leaking memory and blocking the event loop.
