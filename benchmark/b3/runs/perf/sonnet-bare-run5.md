1. Don't ship the proposal as-is: more workers/pool won't fix a blocked event loop or the memory leak, and 16 workers × 50 pool × 6 pods = up to 4800 DB connections vs current 240 — likely blows past Postgres max_connections. Redis caching just masks the slow path for 60s and adds staleness/cache-stampede risk on top of an unfixed root cause.
2. Root cause of the healthz outage: `lookup_geo` calls `requests.get()` synchronously inside an async handler, blocking the whole event loop (all 4 workers' worth of requests, including /healthz) for as long as the GeoIP call takes — fix by using an async HTTP client (httpx) or running it in a threadpool.
3. Root cause of the 1.2-1.6s query: no index covers `(org_id, created_at)`, so Postgres does a full scan + sort of 4.2M rows for every call — add `CREATE INDEX events_org_created_idx ON events (org_id, created_at DESC)`.
4. N+1 query: `serialize_event` does one `SELECT ... FROM users` per event, so 1912 events = 1912 round trips — batch-fetch all actors in one `WHERE id = ANY($1)` query before serializing.
5. Query has no LIMIT and fetches every row in the 30-day window before dedup/slicing in Python — push the limit and dedup into SQL (e.g. `DISTINCT ON (dedupe_key) ... ORDER BY dedupe_key, created_at DESC`, then re-sort and `LIMIT`) so acme's ~1.9k rows aren't all pulled and held in memory per request.
6. Dedup uses `dedupe_key in seen` (list) → O(n²) over event count — switch `seen` to a `set`.
7. Memory leak: `_geo_cache` and `_request_timings` are module-level and never bounded or evicted, growing for the life of the pod (matches the 310MB→2.1GB/20h climb) — cap `_geo_cache` with a TTL/LRU and cap `_request_timings` to a ring buffer (e.g. last N samples), since `/internal/metrics` only needs recent percentiles.
8. After 2-7 land, re-measure before touching worker/pool counts or adding caching — most of the current latency and memory growth should be gone, and any residual scaling need can be sized correctly instead of guessed.
