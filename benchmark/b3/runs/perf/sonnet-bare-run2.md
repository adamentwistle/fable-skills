1. Don't ship the on-call proposal as-is — it papers over the real bugs and the pool math is dangerous (16 workers × 50 conns × 6 pods = up to 4,800 Postgres connections; check max_connections first).
2. Root cause of the slow query: no index on `events(org_id, created_at)` — every call is a sequential scan over 4.2M rows; add a composite index (`org_id, created_at DESC`).
3. The query has no `LIMIT` and no dedup pushed to SQL — it pulls the full 30-day window (1,912 rows for acme) into Python, dedups with an O(n²) `in seen` list scan, then throws most of it away; do the dedup/limit in SQL (e.g. `DISTINCT ON (dedupe_key) ... ORDER BY dedupe_key, created_at DESC` wrapped and limited) or at minimum use a set for `seen` and stop building the full list before slicing.
4. N+1 query: `serialize_event` does one `actor_id` `fetchrow` per event — 1,912 sequential round-trips for acme; batch-fetch all actors in one `WHERE id = ANY($1)` query and join in Python.
5. Root cause of the healthz stalls / probe restarts: `lookup_geo` uses synchronous `requests.get()` inside an async handler — it blocks the entire event loop (all 4 workers' coroutines, including `/healthz`) for up to 2s per uncached IP; switch to an async HTTP client (httpx) or run it in a thread pool. This is also why just adding workers won't fix the freeze — more blocked event loops, not more throughput.
6. Root cause of the memory leak: `_geo_cache` is an unbounded module-level dict that never evicts — it grows for the life of the pod (matches the ~20h climb to 2.1GB); cap it or use a TTL/LRU cache.
7. Same leak pattern in `_request_timings` — appended on every request, never trimmed; bound it (ring buffer or periodic reset) — it's also feeding `/internal/metrics`, so this is inflating your p50/p95 numbers over time too.
8. The proposed Redis cache key (`org_id, since, limit`) will almost never hit: `since` defaults to `datetime.now(timezone.utc) - 30d`, computed fresh to the microsecond on every request with no `since` param (the mobile client's actual case) — bucket/round the default window before using it as a cache key, or the cache buys nothing.
9. Only after 2–7 are in: re-measure latency and pod RSS; then decide if a modest worker/pool bump or the response cache is still worth adding — right now they'd just hide the real bugs and risk exhausting Postgres connections.
