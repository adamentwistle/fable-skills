Don't ship the on-call proposal as-is — it patches symptoms, not the two causes actually producing the 6-12s and the leak, and the Redis part likely won't even hit: `since` defaults to `datetime.now()` computed per request, so unless the mobile client pins `since`, the cache key differs every call.
2. Add a composite index on `events(org_id, created_at DESC)` — there's no index covering this WHERE/ORDER BY, so it's scanning all 4.2M rows per request; this is most of the 1.2-1.6s in the slow-query log.
3. Fix the N+1: `serialize_event` runs a separate `SELECT ... FROM users` per event, awaited one at a time — for acme that's ~1,900 sequential round-trips per request. Batch actor lookups with one `WHERE id = ANY($1)` (or a JOIN in the main query).
4. Fix the event-loop block: `lookup_geo` calls `requests.get` (sync, blocking) inside an async handler, up to 2s per uncached IP. This is why `/healthz` on the same pod goes unresponsive and the liveness probe is killing pods — it's blocking the whole worker's event loop, not a load problem. Switch to an async HTTP client (`httpx.AsyncClient`) or take geo resolution off the request path entirely.
5. Fix the memory leak: `_geo_cache` and `_request_timings` are module-level and never evict — that's the RSS climb to 2.1GB over ~20h, not GC pressure. Cap `_geo_cache` (LRU/TTL) and bound `_request_timings` (ring buffer/reservoir) since `/internal/metrics` still needs to read it.
6. Fix the dedupe/limit logic: dedupe checks `dedupe_key in seen` against a growing list (O(n²)), and the SQL has no `LIMIT` so it always pulls the full 30-day window before truncating in Python. Use a `set` for the seen-check and push `LIMIT` into the query.
7. Re-measure after 2-6 before touching worker/pool counts — once the blocking call and N+1 are gone, 4 workers/10 conns may already be enough; only raise concurrency if profiling still shows contention.
8. If still adding the Redis cache, key it on a normalized/bucketed `since` (or drop `since` from the key when the client omits it) so the common mobile-app case actually gets cache hits.
