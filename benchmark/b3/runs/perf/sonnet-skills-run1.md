Do not ship the on-call proposal as-is: it scales up two subsystems (workers, pool) and slaps a cache in front of a request that has three separate correctness/perf bugs — it will hide the symptom for ~60s windows and make the memory leak worse (more workers each running the same unbounded caches).
2. Root cause of the pod restarts: `lookup_geo` uses synchronous `requests.get` inside an async handler, called once per event serially in `serialize_event`. A cache-miss run of ~1900 events with many distinct IPs blocks that worker's whole event loop for seconds at a time, including `/healthz` on that worker — fix by using an async HTTP client (httpx.AsyncClient) or moving geo lookups off the request path.
3. Root cause of the RSS leak: `_geo_cache` and `_request_timings` are module-level, grow forever, never evicted — bound `_geo_cache` (LRU with a maxsize, or TTL) and cap/rotate `_request_timings` (fixed-size ring buffer).
4. Root cause of the 1.2-1.6s SQL time: no index covers `(org_id, created_at)` — `events` only has indexes on `actor_id` and `kind`, so this is a sequential-scan-and-sort over 4.2M rows every call; add `CREATE INDEX events_org_created_idx ON events (org_id, created_at DESC)`.
5. Second, hidden cost per request: `serialize_event` does one `actor` SELECT per event (N+1, ~1900 round trips for acme) — batch it into a single `WHERE id = ANY($actor_ids)` query and build a lookup dict.
6. Dedup bug: `if ev["dedupe_key"] in seen` against a growing `list` is O(n²) on top of everything else — use a `set`.
7. The SQL has no LIMIT and ignores the client's `limit=1000` until after fetch+dedup+serialize — push `LIMIT` (post-dedupe, so likely need a window function or a two-step query) so you don't fetch/serialize more rows than requested.
8. Once 2-7 are done, re-measure p50/p95 and pod RSS over 20h before deciding whether the worker/pool bump is even still needed — likely much less necessary once the event loop stops blocking and query cost drops.
9. Redis response caching can be revisited afterward as a genuine latency win for repeat polling (mobile clients likely re-poll the same window), but only once the underlying handler is correct — caching a handler that leaks memory and blocks the loop just delays both problems by 60 seconds.
