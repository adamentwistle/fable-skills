1. Cache has no invalidation — it's keyed on nothing and never checked against the file, so store the file's mtime (and size) alongside the data and reload when it differs.
2. `_cache is None` conflates "not loaded" with "loaded and empty/null" — a config file containing `null` reloads every call; use a distinct sentinel or a separate `_loaded` flag.
3. `path` is ignored after the first call — a second call with a different path silently returns the first file's data, so key the cache by resolved absolute path in a dict.
4. Not thread-safe — two threads can both see `None` and race on the parse, so guard load-and-store with a lock (double-checked).
5. A failed read leaves `_cache` as `None` and re-raises on every call — fine, but partial/truncated writes get cached permanently, so only assign `_cache` after `json.load` succeeds and treat a torn read as a reload next call.
6. No way to force a refresh — add an explicit `clear_config_cache()` / `force=True` for callers that know the file changed.

Tempting fixes that do NOT address the root cause: adding a time-based TTL (still serves stale data for the window and re-reads when nothing changed — it masks the missing invalidation rather than fixing it); calling `get_config.cache_clear()`-style tricks or switching to `functools.lru_cache` (same never-invalidated cache, now keyed by path — it fixes finding 3 only); making the read thread-safe (fixes a different bug — a locked stale cache is still stale); comparing mtime alone at 1-second filesystem granularity (misses same-second rewrites — pair it with size or content hash); watching the file with a background thread/inotify (correct-ish but adds a lifecycle you must shut down, and still needs the mtime check as fallback on platforms where events drop).
